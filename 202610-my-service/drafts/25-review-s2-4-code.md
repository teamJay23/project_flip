### 한 번만 처리되는지

- `requestCards`는 `return`이 한 번뿐인 함수라, 결과가 두 번 나올 수 없다. `handleResult`도 한 번만 불린다.
- 결과가 먼저 오면: `await` 다음 줄부터 `return`·`finally`까지 중간에 끊기지 않고 이어서 돈다 → 타이머가 그 사이에 끼어들 수 없다 → `clearTimeout`(432줄).
- 헤더는 받았는데 **본문을 읽는 중**에 60초가 되면: `abort()`가 `res.json()`도 끊는다 → `catch` → `aborted`가 true → `TIMEOUT`. 시험으로 확인했다(3번 "본문 읽는 중 60초"). `BAD_JSON`으로 잘못 가지 않는다.

### 로딩에 갇히는 길 / `isStarted` 되돌림

- 실패는 모두 `showFail` → `resetStart()`로 간다. `requestCards` 안에서 못 잡은 예외(예: 아주 옛 브라우저에 `AbortController`가 없음 → 398줄에서 멈춤)도 바깥 안전망이 잡아 `showFail('service')`. **갇히는 길 없음.**
- 성공이면 `isStarted`가 true로 남고 로딩 화면에 임시 표시가 남는다. 3단계 전까지 **의도된 것**이다(G-8 ⑤에서 시험 안내만 더하자고 제안).
- 남는 길 1개: 휴대폰이 화면 뒤로 가서 타이머가 멈추면 60초가 늦어진다 → 24번 0-3대로 **S2-7 범위**. 이번 검토에서는 문제로 세지 않았다.

## 2. Apps Script 웹 앱 특성 (근거)

| 무엇 | 확인 결과 | 근거 |
|---|---|---|
| `/exec`에 POST → 302로 `script.googleusercontent.com`에 보냄 | 맞다. 공식 문서: Content service 결과는 "one-time URL at script.googleusercontent.com"으로 리다이렉트되고, 받는 쪽은 "follow redirects"해야 한다 | **확인**: developers.google.com/apps-script/guides/content "Redirects" (2026-10-27) |
| `fetch`가 302를 따라가는지 | 기본값(`redirect: 'follow'`)이라 따라간다. 302 + POST는 표준에 따라 **GET으로 바뀌고 본문은 빠진다** | Fetch 표준 "HTTP-redirect fetch" (기억 기준, 이번에 다시 열지 않음) |
| `doPost`가 몇 번 도는지 | 첫 POST 때 1번. 두 번째 GET은 저장된 답만 가져온다 → 2-3 시험(실행 기록 1번)이 성립한다 | **추정** (공식 문서는 "one-time URL"이라고만 함). 2-3 시험으로 실제 확인됨 |
| `text/plain;charset=utf-8`이 사전 요청을 피하는지 | 피한다. 표준은 `Content-Type`의 **본 종류**(`text/plain`)만 보고, `;charset=…`가 붙어도 "안전한 헤더"로 본다. 다른 헤더도 안 넣었고 `signal`은 헤더를 만들지 않는다 | Fetch 표준 "CORS-safelisted request-header" (기억 기준). **실제 확인은 체크리스트 첫 줄**(Network 탭 `OPTIONS` 없음) |
| 리다이렉트된 답에 CORS 허락 표시가 있는지 | 있다고 널리 알려져 있다(`Access-Control-Allow-Origin: *`). 그래서 HTML이 답을 읽을 수 있다 | **추정** (공식 문서에 없음). 체크리스트 6-b가 성공하면 확인됨 |
| 서버 쪽 본문 읽기 | `card-api.gs`는 `e.postData.contents`를 `JSON.parse` → `text/plain`이어도 그대로 읽힌다 | 사본 코드 확인 |
| 배포 권한이 잘못됐을 때 ("나만" / "Google 계정 있는 사람") | `/exec`가 Google 로그인 페이지로 보낸다 → 그 페이지엔 CORS 허락 표시가 없다 → 브라우저가 답을 버리고 `fetch`가 실패 → `res`가 비어 있음 → **`FETCH_FAILED` → 서비스 문구**(인터넷 켜짐). `fetch`는 기본으로 다른 사이트에 로그인 쿠키를 안 보내므로, **PC에서 Google에 로그인해 있어도 똑같이 실패**한다 | **추정**. G-2에서 시크릿 창 시험을 제안 |
| 주소가 틀렸을 때 (7-b 구분 시험) | Google의 404 HTML 페이지 → CORS 허락 표시 없음 → 위와 같은 길 → `FETCH_FAILED` → 서비스 | **추정**. 결과(서비스 문구)는 계획 기대와 같음 |
| `doPost`가 예외로 멈췄을 때 | Google 오류 HTML이 오는데, 이것도 허락 표시가 없을 가능성이 크다 → `BAD_JSON`이 아니라 `FETCH_FAILED`로 갈 수 있다 | **추정**. G-5 |
| Apps Script 쪽 50초 | `UrlFetchApp.fetch`의 `timeoutSeconds`는 공식 매개변수다(기본 360초). 50초 설정은 유효하다 | **확인**: developers.google.com/apps-script/reference/url-fetch/url-fetch-app (2026-10-27) |
| PC에서 파일을 바로 열 때(`file://`) | 출처가 `null`로 가지만 허락 표시가 `*`이면 읽힌다 | **추정**. 안 되면 Vercel 브랜치 주소로 PC에서 시험 |

**G-1. 7-c 시험(비행기 모드)에 "와이파이도 꺼졌는지 확인" 넣기** — 고치면 좋음 / 위치: 24번 4번 표 7-c 줄

- 실제 상황: admin이 비행기 모드를 켜고 시험했는데 카드가 만들어지거나 "잠시 후…"가 나와서, 코드가 틀린 줄 알고 헤맨다.
- 고치는 방법: "비행기 모드 켜기 → 제어 센터에서 **와이파이·셀룰러가 둘 다 꺼졌는지** 확인 → [카드 만들기]"로 적는다.

**G-2. 배포 권한 확인 줄 더하기 (시크릿 창)** — 고치면 좋음 / 위치: 24번 4번 표

- 실제 상황: 6-b가 계속 "잠시 후…"로 실패하는데, 코드·Gemini·인터넷 중 어디가 문제인지 모른다. 또 나중에 실제 사용자는 Google 로그인이 안 된 휴대폰일 수 있다.
- 고치는 방법: 체크리스트 맨 위에 "Apps Script 배포 관리에서 액세스 권한 = **모든 사용자** 확인"과 "**시크릿 창**(로그인 안 된 창)에서 6-b 한 번 더"를 넣는다. 6-b가 계속 서비스 문구로 실패하면 가장 먼저 이것을 보라고 한 줄 적어 둔다.

**G-3. 6-c 시험 줄은 "기다린 뒤 바로 끝내기"로** — 고치면 좋음 / 위치: 24번 4번 표 6-c 줄
- 문제: 화면이 60초에 요청을 끊어도(abort) **Apps Script는 멈추지 않는다.** 계획대로 `Utilities.sleep(70000);`만 넣으면 70초 뒤에 Gemini를 **진짜로 부른다**(무료 사용량을 쓰고, 카드는 아무도 안 받는다).
- 실제 상황: 6-c를 몇 번 되풀이하면 그만큼 Gemini 호출이 쌓인다. 실행 기록에 "OK"가 찍혀서 "성공했는데 왜 실패 문구가?" 하고 헷갈릴 수 있다.
- 고치는 방법: 시험 때만 넣는 줄을 `Utilities.sleep(70000); return reply_({ ok: false, reason: 'OTHER' });`로 한다(Gemini를 부르지 않음). 시험 뒤 두 줄 다 빼고 새 버전 배포 — 계획 4번 아래 주의 문장과 같다.
- 같은 이유로 참고: 실제 사용자가 60초 실패 뒤 바로 다시 누르면, 서버에서는 앞 요청이 아직 돌고 있어 **실행 기록에 2번** 남을 수 있다. 2-3(두 번 누름) 시험과는 상관없다(그때는 60초 실패가 없음).

**G-8. 체크리스트에 빠진 시나리오** — 고치면 좋음 / 위치: 24번 4번 표

- ② **로딩 중에 인터넷 끊기**: 누른 뒤 1~2초 안에 비행기 모드. 기대: 대부분 "인터넷…" 문구. 브라우저가 꺼짐을 늦게 알아채면 "잠시 후…"가 나올 수도 있다 → 6-1 표 2행 설명대로 **둘 다 통과로 본다**고 미리 적어 둔다.
- ③ **7-b 같은 실패 2번** (02 8번 표에는 있는데 24번 표에 없음): 비행기 모드 실패를 2번 → 두 번 다 같은 문구.

- ⑤ **성공 뒤에는 새로고침해야 다음 시험을 할 수 있다**는 안내: 성공하면 임시 표시에서 멈춘다(3단계 전까지 의도). 모르면 "버튼이 사라졌다"고 오해할 수 있다.

## [참고]

**G-4. 50초(서버) ↔ 60초(화면) 사이 여유가 생각보다 작을 수 있음** — 참고 / 위치: 199줄 주석, `card-api.gs` `FETCH_TIMEOUT_SEC`
- 서버의 50초는 **Gemini를 기다리는 시간만**이다. 앞뒤에 Apps Script 시작 시간, 리다이렉트 한 번, 휴대폰 통신 시간이 더해진다.
- 실제 상황: Gemini가 48초 걸리면 서버는 성공했는데 화면은 60초에 `TIMEOUT`을 낼 수 있다. 사용자에게는 "잠시 후…"라 PRD 위반은 아니다.
- 할 일: S2-6(최대 길이 원문 시간 재기) 때 실행 기록의 `ms`와 화면에서 걸린 시간을 같이 적어, 차이가 몇 초인지 본다. 지금 고칠 것은 없다.

**G-5. `BAD_JSON` 주석의 예시가 실제와 다를 수 있음** — 참고 / 위치: 428줄 주석 "예: Apps Script 오류 페이지"
- 2번 표대로, Google 오류 페이지는 CORS 허락 표시가 없어서 `BAD_JSON`이 아니라 **`FETCH_FAILED`로 갈 가능성이 크다**(추정). 사용자 문구는 둘 다 "잠시 후…"라 동작에는 영향이 없다.
- 영향: 나중에 콘솔 코드로 원인을 찾을 때 "`FETCH_FAILED`니까 인터넷/주소 문제"라고만 생각하기 쉽다. 배포 권한·서버 예외도 `FETCH_FAILED`일 수 있다는 점을 02 6-1 표 2행 설명이나 이 주석에 한 줄 남기면 좋다. 고친다면 주석을 "예: JSON이 아닌 응답"으로.

**G-6. 콘솔에 `undefined`가 찍히는 경우** — 참고 / 위치: 412줄
- `{ok:false, reason:'KEY'}`처럼 `status`가 없으면 콘솔에 `[Flip] KEY undefined`, 본문이 `null`이면 `[Flip] null null`처럼 보인다(시험 결과 3번).
- 잘못된 동작은 아니지만, 입문자가 보면 "오류가 났다"로 읽을 수 있다. 원하면 `console.warn('[Flip]', (data && data.reason) || 'NO_REASON', (data && data.status) || '');` 정도로 바꿀 수 있다. 안 바꿔도 된다.

**G-7. 휴대폰에서는 콘솔이 안 보인다** — 참고 / 위치: 24번 4번 표 6-c·7-d 줄
- 휴대폰 브라우저는 개발자 도구(콘솔)를 바로 볼 수 없다. "콘솔 `TIMEOUT`", "콘솔 `KEY`" 확인은 **PC에서**, 휴대폰에서는 **문구만** 보면 된다고 적어 두면 좋다. 7-d의 `KEY`는 Apps Script **실행 기록**(`reason: "KEY"`)으로도 확인할 수 있다.

**G-9. 모바일 브라우저 지원 (`AbortController`, `navigator.onLine`)** — 참고
- `AbortController`로 `fetch` 끊기: iOS Safari 12.1 이상, Android Chrome 66 이상에서 된다(MDN 호환표 기준, 기억 — 이번에 다시 열지 않음). 지금 쓰는 휴대폰은 모두 해당한다. 혹시 없으면 398줄에서 멈추지만 바깥 안전망이 받아 "잠시 후…"로 간다 → **갇히지 않는다.**
- `navigator.onLine`: `false`는 믿을 만하지만(비행기 모드 등), `true`는 "어딘가에 연결됨"일 뿐 인터넷이 된다는 뜻이 아니다(와이파이는 잡혔는데 바깥으로 안 나가는 경우). 이때는 "잠시 후…"가 나온다 — 02 6-1 표 아래 설명대로 **받아들인 한계**다. 요청 중에 끊겼을 때 값이 늦게 바뀌는 것은 G-8 ②.
- 다른 앱 갔다 오기(타이머 멈춤)는 S2-7.

**G-10. 7-b 구분 시험의 "주소 끝 한 글자"** — 참고 / 위치: 24번 4번 표 7-b 구분 줄
- 주소 맨 끝은 `/exec`다. 끝 글자를 바꾸면 `/exed`가 된다. 이것도 Google 404라 결과(서비스 문구)는 같지만, "배포 ID가 틀린 경우"를 보려는 뜻이면 **`/s/` 뒤 긴 ID 가운데 한 글자**를 바꾸라고 적는 게 분명하다. 시험 뒤 되돌리기, 커밋하지 않기는 계획대로.

**G-11. 줄바꿈 경고** — 참고
- `git diff` 때 `LF will be replaced by CRLF` 경고가 나온다. 21 검토 G-2와 같은 Windows Git 설정 탓이라 무시해도 된다.

## [괜찮은 점]

- **계획 초안을 그대로 옮겼다.** 2·3번 코드 블록과 diff가 주석 한 군데 말고 같다.
- **0행(보내기 전 꺼짐)을 맨 앞에 둬서** "fetch 실패 = 인터넷"으로 묶는 실수(02-2)를 피했다.
- **`res`를 `null`로 시작해 "응답을 받았는지"로 2행·3행을 나눴다.** 단순하고 읽기 쉽다.
- **`ok !== true`로 비교해** `null`·이상한 값도 서비스 문제로 모았다.
- **본문 읽는 중 60초도 `TIMEOUT`으로 간다.** `signal`이 `res.json()`까지 덮는다.
- **`finally`로 타이머를 끄는 곳이 한 군데뿐이다.** 어느 길로 끝나도 타이머가 남지 않는다.
- **바깥 안전망이 있어 13 1-7 걱정(로딩에 갇힘, `isStarted`가 true로 남음)이 사라졌다.**
- **콘솔에는 짧은 코드와 숫자만** 남는다. 원문·카드·키·오류 문장 없음.
- **가짜 장치가 0줄**이고, 지우기 전에 `fake-responses.md`로 옮겨 두었다.
- **서버(50초) < 화면(60초)** 순서를 주석에 적어 나중에 바꿀 때 놓치지 않게 했다.
