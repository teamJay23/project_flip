> 용어 풀이
> - **세션(session)** = 한 사람이 앱을 열고 쓰다가 닫을 때까지의 한 번의 사용. 여기서는 "브라우저 탭 하나"로 본다
> - **DB(데이터베이스)** = 기록을 줄과 칸으로 쌓아 두고 꺼내 쓰는 저장소. Google Sheet도 간단한 DB처럼 쓸 수 있다
> - **메모리 변수** = 코드 안의 `let queue = …` 같은 값. 페이지를 새로고침하면 사라진다
> - **sessionStorage** = 브라우저가 **탭 하나마다** 따로 갖는 작은 저장 공간. 새로고침해도 남고, 탭을 닫으면 지워진다
> - **localStorage** = 브라우저에 **계속** 남는 작은 저장 공간. 탭을 닫아도 남는다. 다른 기기와는 공유되지 않는다
> - **익명 세션 ID** = 이름·이메일 없이, 브라우저가 만든 무작위 글자로 "이 사용"을 구분하는 번호 (예: `3f2a9c1e-…`)
> - **scope(권한 범위)** = Google 로그인 때 "이 앱이 내 정보 중 무엇을 볼 수 있는지" 정하는 항목

## 0. 먼저 알아둘 것 (3가지)

1. **지금 세션 기록은 어디에도 저장되지 않는다.** 강사님 질문의 "사용자별 session으로 저장되고 있다"는 지금 코드와 다르다. 학습 상태는 **메모리 변수에만** 있어서, 새로고침하면 전부 사라진다. 코드 4개 파일에서 `localStorage`, `sessionStorage`, 쿠키를 검색했더니 **0개**였다. 자세한 내용은 1번에 있다.
2. **범위 확인이 필요하다.** 프로젝트 `CLAUDE.md`에는 "검증용 기능(통계, 로그인 등)을 지금 미리 만들지 않는다"고 적혀 있다. 세션 기록 저장은 강사님 지시로 **지금** 들어온 일이다. 그래서 CLAUDE.md와 PRD를 고쳐야 한다(팀 질문 1).
   - "사용 패턴 기반 제안"(2번의 제공 데이터)은 통계 기능에 가깝다. 그래서 이번에는 **설계만** 하고 만들지 않는 것으로 적었다.
3. **"Google 계정으로 나이·거주 지역 받기"는 기술적으로 가능은 하지만 어렵다.** 추가 권한, Google 앱 검증, 개인정보 동의가 필요하다. 그리고 PRD 기능 19의 "사용자 ID와 이메일만 저장"과 부딪힌다. 대안으로 "첫 사용 때 선택 입력"이 있다 (5번).

## 3. 로그인 없이 Google Sheet에 저장하는 방법

### 3-1. 익명 세션 ID 만들기

- 브라우저에서 무작위 값을 만든다: `crypto.randomUUID()` (브라우저에 들어 있는 "겹치지 않는 무작위 번호 만들기" 명령).
  - 이 명령은 https 주소에서 동작한다. Vercel 배포 주소는 https라서 괜찮다. 파일을 더블클릭해 연 경우(`file://`)에도 되는지는 **확인 필요**다. 안 되면 **"지금 시각 + `Math.random()` 무작위 값"** 을 이어 붙여 대신 쓴다. `Math.random()` 하나만 쓰면 드물게 겹칠 수 있기 때문이다. (이 경우 3-6번의 UUID 모양 검사도 이 형식을 받도록 맞춘다)
- 만든 값은 **sessionStorage**에 넣어 둔다. 그러면 PRD 기능 8과 똑같이 동작한다.
  - 새로고침 → 같은 ID (같은 세션으로 이어짐)
  - 탭을 닫았다 다시 열기 → 새 ID (새 세션)
- 이름·이메일·기기 정보는 넣지 않는다. 이 ID만으로는 누구인지 알 수 없다.
- **같은 사람이 다음 날 다시 왔는지**(PRD 2번 "확인 필요")는 이 방식으로는 알 수 없다. 알려면 localStorage에 "브라우저 ID"를 하나 더 두어야 한다. 이건 사용자를 계속 알아보는 일이라 고지가 더 필요하다 → 팀 질문 4.

### 3-2. 시트 설계 (탭 3개)

시트 한 파일 안에 탭 3개를 둔다. 지금 있는 `test01` 탭은 그대로 둔다(시험 기록).

**탭 1: `stacks` — 생성 시도 1번 = 1줄 (실패도 기록)**

| 열 이름 | 뜻 | 예시 |
|---|---|---|
| session_id | 익명 세션 ID | `3f2a9c1e-8b7d-4e21-9a0f-5c6d7e8f9a0b` |
| stack_id | 생성 시도 번호 (Apps Script가 붙임) | `S-20261024-153012-a1b2` |
| created_at | 생성 시도 시각 | `2026-10-24 15:30:12` |
| source_unit | 원문을 센 단위 | `chars` / `words` |
| source_count | 원문 길이 | `465` |
| source_text | 원문 (팀 질문 2 결정에 따름) | (비움) |
| result | 결과 | `ok` / `source_problem` / `service_problem` |
| reason | 실패 이유 (02 계획 5번) | `KEY` / `QUOTA` / `BAD_RESPONSE` / 빈칸 |
| card_count | 받은 카드 수 (20장 자르기 전) | `8` |
| duration_ms | 걸린 시간 (1/1000초 단위) | `6230` |
| model | 사용한 모델 | `gemini-2.5-flash-lite` |
| tokens_in / tokens_out | 입력·출력 토큰 수 (`usageMetadata`) | `1480` / `960` |

- "인터넷 끊김"은 요청이 Apps Script에 닿지 못한 경우라서 기록할 수 없다. 이건 한계로 받아들인다.

**탭 2: `cards` — 카드 1장 = 1줄 (생성 성공 때만)**

| 열 이름 | 뜻 | 예시 |
|---|---|---|
| stack_id | 어느 생성 시도의 카드인지 | `S-20261024-153012-a1b2` |
| card_order | 생성 순서 (1~20) | `3` |
| front | 앞면 질문 | `망각곡선에서 기억은 언제 가장 빠르게 줄어드나?` |
| back | 뒷면 답 | `학습 직후. 시간이 지날수록 줄어드는 속도는 느려진다.` |

- 카드를 저장할지도 팀 질문 2에 함께 들어 있다 (카드에도 원문 내용이 들어 있으므로).

**탭 3: `events` — 사용자 행동 1번 = 1줄**

| 열 이름 | 뜻 | 예시 |
|---|---|---|
| session_id | 익명 세션 ID | `3f2a9c1e-…` |
| stack_id | 어느 stack에서 | `S-20261024-153012-a1b2` |
| at | 행동 시각 | `2026-10-24 15:31:40` |
| type | 행동 종류 | `know` / `dont_know` / `complete` / `restudy` / `new_stack` / `guide_view` |
| card_order | 어느 카드 (해당될 때만) | `3` |
| round | 몇 번째 라운드 | `2` |
| side | 고를 때 앞면이었나 뒷면이었나 | `front` / `back` |

- 이 설계는 `80-데이터정의.md`(한 줄 = 카드 1장 + 학습 상태 + 승인 칸)와 다르다. 다르게 한 이유는 "지금 상태"를 빼고 "지난 기록"만 남기려는 것이다. `80-데이터정의.md`를 고칠지는 팀 질문 5.
- 크기 확인: Google Sheets는 파일 하나에 **최대 2,000만 셀 또는 100MB**까지 쓸 수 있다. 공식 도움말 원문은 "Up to 20 million cells or 100MB"다 (https://support.google.com/docs/answer/37603, 2026-10-24 확인).
  - stack 1개(카드 20장, 라운드 3번)에 드는 칸은 대략 이렇다: `stacks` 13칸 + `cards` 80칸 + `events` 약 280칸(40줄 × 7칸) = **약 400칸**.
  - 2,000만 셀이면 **약 5만 stack**이다(추정). Phase 3 규모에는 충분하다.
  - 이 계산은 `source_text`(원문) 칸을 **비운 경우**다. 원문 전체를 저장하면(팀 질문 2의 (다)) 한 칸에 최대 5,000자가 들어가서 **100MB 한도가 먼저 찰 수 있다.**
  - 실제로는 셀 한도보다 **속도**(Apps Script 쓰기, 시트 열기)가 먼저 문제가 된다. 셀 한도는 걱정하지 않아도 되고, 옮길 때를 정하는 실제 기준은 4-3번 ②·③이다.

### 3-3. 보내는 방법 (요청 수를 줄이기)

| 무엇을 | 언제 한 번에 보내나 | 누가 시트에 쓰나 |
|---|---|---|
| `stacks` + `cards` | AI 카드 생성이 끝났을 때 | **Apps Script가 직접** — 카드를 만든 바로 그 실행 안에서 쓴다. 브라우저가 따로 보낼 필요가 없다. 단, 이 기록 코드는 **2단계(02 계획 S2-0~S2-7)가 다 끝난 뒤** D-2에서 더한다 (결정 A) |
| `events` (안다/모른다) | **라운드가 끝날 때** 그 라운드 기록을 모아서 한 번 | 브라우저 → Apps Script |
| `events` (완료, 다시 학습, 새로 만들기) | 그 버튼을 누를 때 | 브라우저 → Apps Script |

- 안다/모른다를 누를 때마다 보내면 요청이 너무 많아진다(카드 20장 × 라운드 수). 그래서 라운드 단위로 모은다.
- 한계: 라운드 중간에 탭을 닫으면 그 라운드 기록은 빠진다. MVP에서는 받아들인다.
- 여러 사람이 동시에 쓰면 줄이 섞이거나 겹칠 수 있다. `LockService`(Apps Script에서 "한 번에 한 실행만 쓰게" 줄 세우는 기능)로 쓰는 부분을 감싼다. 코드 몇 줄이면 된다.

### 3-4. 기존 `Code.gs` 저장 시험과 어떻게 이어지나

- 웹 앱 주소를 아는 누구나 가짜 기록을 보낼 수 있다. 대책은 3-6번에 있다.

### 3-5. 기록이 실패해도 앱은 멈추지 않는다 (규칙)

> **규칙: 시트 기록이 실패해도 카드 생성과 학습은 막지 않는다. 사용자 화면에는 아무것도 띄우지 않고, 개발자 기록에만 남긴다.**

왜 필요한가: 기록은 "있으면 좋은 것"이지 학습 흐름의 일부가 아니다. 카드는 잘 만들어졌는데 시트 쓰기가 실패했다고 사용자가 "잠시 후 다시 시도해주세요"를 보면 안 된다.

| 어디서 | 이렇게 한다 |
|---|---|
| Apps Script (D-2) | ① **카드 생성 결과를 먼저 정한다.** ② 시트 쓰기는 따로 `try/catch`(실패해도 멈추지 않게 감싸는 문법)로 감싼다. ③ 쓰기가 실패해도 응답은 `{ ok: true, cards }` 그대로 보낸다. 실패는 Apps Script 실행 기록에만 남긴다 |
| Apps Script 잠금 | `LockService` 대기 시간은 **짧게(예: 5초)** 둔다. 못 잡으면 기록만 건너뛴다. 60초 대기 예산(PRD 6-c)을 잡아먹지 않게 하려는 것이다 |
| 브라우저 (D-3·D-4) | `events`를 보낸 뒤 **결과를 기다리지 않는다.** 실패해도 화면에 아무것도 띄우지 않는다. 개발자 확인용으로 콘솔에만 남긴다 |

> **주의: 이 규칙은 "기록 쓰기"에만 해당한다.** 카드 생성 요청 자체가 3-6번 검사(하루 상한, 원문 길이 등)에 걸린 경우는 다르다. 이때는 카드가 만들어지지 않았으므로 조용히 넘어가면 안 된다. 사용자에게 **"잠시 후 다시 시도해주세요"** 를 보여야 한다 (3-6번 처리 표, 02 계획 기능 7 "서비스 문제").

### 3-6. 공개 주소로 아무나 쓰는 위험 막기 (MVP 최소안)

웹 앱 주소는 브라우저 코드(`config.js`)에 들어가므로 결국 공개된다. 그래서 다음 세 가지 위험이 있다.
- **가짜·장난 기록**이 섞여 Phase 3 분석(완료율, 라운드 수)이 틀어진다.
- **대량 쓰기**로 시트 한도, Apps Script 한도, (카드 생성 요청이면) **Gemini 무료 한도**를 다 써 버린다. 그러면 실제 사용자에게 "잠시 후 다시 시도해주세요"가 뜬다.
- **수식 주입**: 시트에 `=`로 시작하는 글이 들어가면, 시트가 그것을 글이 아니라 **계산식**으로 실행한다. 예를 들어 `=IMPORTXML("http://…")`는 팀원이 시트를 열 때 바깥 주소로 요청을 보낼 수 있다.

Apps Script는 요청을 처리하기 **전에** 아래를 검사한다. 검사에 걸렸을 때 어떻게 할지는 **요청 종류마다 다르다.**

**검사에 걸렸을 때 처리 (v1.3)**

| 요청 종류 | 예 | 검사에 걸리면 | Apps Script 응답 | 사용자 화면 |
|---|---|---|---|---|
| **카드 생성** (`generate`) | 하루 생성 상한 초과 | Gemini를 부르지 않는다. 시트에도 쓰지 않는다 | `{ ok: false, reason: "QUOTA" }` | **"잠시 후 다시 시도해주세요"** (02 기능 7 서비스 문제) |
| **카드 생성** (`generate`) | 그 밖의 검사에 걸림: 원문이 너무 김, 세션 ID 모양이 이상함, 모르는 `type` 등 | Gemini를 부르지 않는다. 시트에도 쓰지 않는다 | `{ ok: false, reason: "BAD_REQUEST" }` | **"잠시 후 다시 시도해주세요"** (02 계획 6-1번 표 4번 `ok: false` → 서비스 문제) |
| **기록 쓰기** (`events`, 생성 뒤 `stacks`·`cards` 기록) | 숫자 범위 밖, 줄 수 초과, 하루 쓰기 상한 초과 등 | **쓰지 않고 조용히 버린다** | 응답을 보내도 브라우저가 기다리지 않음 | **아무것도 안 띄움** (3-5번) |

- 왜 다르게 하나: 카드 생성이 막히면 사용자는 카드를 못 받는다. 아무것도 안 띄우면 로딩 화면이 60초 동안 멈춰 있다가 시간 초과가 된다. 반대로 기록은 실패해도 사용자에게 아무 영향이 없다.
- 원문이 너무 긴 경우는 원래 앱 화면의 길이 검사(PRD 기능 3)에서 먼저 막힌다. 그런데도 Apps Script까지 왔다면 화면을 거치지 않고 직접 보낸 요청이라는 뜻이다. 그래서 "원문 문제"가 아니라 "서비스 문제"로 처리한다.
- `BAD_REQUEST`는 02 계획 5번 `reason` 표에 없는 새 값이다. 화면 문구는 `OTHER`와 같이 "서비스 문제"이고, 개발자 기록에서 구분하려는 것이다. 02 5번 표에 더할지는 다음 02 수정 때 정한다.

| 대책 | 쉬운 설명 | 기준 |
|---|---|---|
| ① `type` 허용 목록 | 정해 둔 종류만 받는다 | `generate`, `events` / `events` 안의 `type`은 `know`·`dont_know`·`complete`·`restudy`·`new_stack`·`guide_view`만 |
| ② 세션 ID 모양 검사 | 세션 ID가 UUID(`8자-4자-4자-4자-12자`, 0~9·a~f) 모양인지 본다 | 모양이 다르면 버림 (3-1번 대체 형식을 쓰면 그 모양도 허용) |
| ③ 숫자 범위 검사 | 숫자 칸에 엉뚱한 값이 못 들어오게 한다 | `card_order` 1~20, `round` 1~50, 요청 1번에 `events` 최대 20줄 |
| ④ 글자 길이 제한 | 아주 긴 글로 시트를 채우는 것을 막는다 | 카드 앞·뒷면은 각각 예: 500자 이하 (숫자는 만들면서 정함) |
| ⑤ 수식 주입 막기 | 시트에 쓰는 **모든 글 값 앞에 `'`(작은따옴표)를 붙인다.** 그러면 `=`로 시작해도 시트가 글로 저장한다 | 원문, 카드, `events`의 글 칸 전부 |
| ⑥ 하루 상한 | Apps Script가 오늘 쓴 줄 수(또는 카드 생성 횟수)를 세어 두고, 넘으면 거절한다. 카드 생성이 거절되면 `QUOTA` → "잠시 후 다시 시도해주세요", 기록 쓰기가 거절되면 조용히 버린다(위 처리 표). 숫자는 `PropertiesService`(Apps Script 안의 작은 저장 공간)에 날짜별로 둔다 | **숫자는 팀 질문 10** (02 계획 질문 5 "하루 호출 수 제한"과 함께 정함) |

- **한계:** 이렇게 해도 "진짜 사용자의 기록인지"는 증명할 수 없다. 그래서 Phase 3 분석 때(D-6) **이상한 값을 먼저 걸러 보는 단계**를 둔다. 예: 한 세션에 이벤트가 너무 많음, 아주 짧은 시간에 몰린 기록.

### 5-1. 기본 Google 로그인으로 받을 수 있는 정보

### 5-2. 나이·지역을 받으려면 필요한 추가 scope (People API)

| scope | Google 설명 (원문) | 받을 수 있는 것 | 한계 |
|---|---|---|---|
| `user.birthday.read` | "See and download your exact date of birth" | 생년월일 | 사용자가 Google 계정에 적어 둔 경우만. **정확한 생년월일**이라 필요보다 많이 받는다 |
| `profile.agerange.read` | (OAuth scope 목록 페이지에는 없고, People API `people.get`의 권한 목록에만 있음) | 나이 범위 | **값이 세 가지뿐이다:** `LESS_THAN_EIGHTEEN`(18세 미만) / `EIGHTEEN_TO_TWENTY`(18~20세) / `TWENTY_ONE_OR_OLDER`(21세 이상). 직장인은 대부분 "21세 이상" 하나로 나온다 → **"20대/30대" 구분은 불가능하다. 우리 목적에는 쓸모없다** (출처: https://developers.google.com/people/api/rest/v1/people, 검토 담당 2026-10-24 확인) |
| `user.addresses.read` | "View your street addresses" | 도로명 주소 | 대부분의 사용자가 Google 계정에 주소를 적어 두지 않는다. **거리 주소까지** 받게 되어 과하다 |

출처 (2026-10-24 확인):
- scope 목록: https://developers.google.com/identity/protocols/oauth2/scopes
- People API 권한 목록: https://developers.google.com/people/api/rest/v1/people/get

### 5-3. Google 앱 검증이 필요한가

- Google 공식 도움말(https://support.google.com/cloud/answer/13463073, 2026-10-24 확인):
  - 민감하지 않은 scope만 쓰면 앱 검증이 **꼭 필요하지는 않다** ("it is not mandatory").
  - **민감(sensitive)·제한(restricted) scope를 쓰면 접근을 받기 전에 앱 검증을 마쳐야 한다** ("must complete Google's OAuth app verification before being granted access").
- 생년월일·주소 scope가 "민감"으로 분류되는지는 **확인 필요**하다. Google Cloud 콘솔에서 scope를 추가하면 "non-sensitive / sensitive / restricted"가 자동으로 표시된다. → **PRD 7단계 전에 Cloud 콘솔에서 scope를 추가해 보고 분류를 기록한다** (짧은 작업).
- 검증 없이 쓸 수 있는 경우(https://support.google.com/cloud/answer/13464323, 2026-10-24 확인):
  - 개발·테스트 상태의 앱: **사용자 100명 상한**이 있고, 로그인 때 "확인되지 않은 앱" 경고 화면이 뜬다.
  - 개인용(100명 미만)
- 정리하면 이렇다. Phase 3 검증을 100명 미만으로 하면 검증 없이도 시험할 수는 있다. 하지만 **경고 화면이 뜨면 사용자가 겁을 먹고 나갈 수 있다.**

### 5-4. 개인정보 동의 (법률 판단은 전문가 확인 필요)

- 생년월일·주소는 개인정보다. 모으려면 **무엇을, 왜, 얼마 동안** 보관하는지 알리고 동의를 받아야 한다(개인정보 보호법의 일반 원칙). 만 14세 미만이면 보호자 동의가 따로 필요하다 **(확인 필요, 근거 조항 미기재)**.
- **PRD 기능 19 규칙과 부딪힌다:** "저장하는 사용자 정보는 사용자 ID와 이메일 두 가지뿐이다(개인정보는 적게 모을수록 좋음)". 나이·지역을 받으려면 이 규칙을 고쳐야 한다.
- 정확한 법적 의무는 **강사님 또는 전문가 확인 필요** (PRD 10번 #8과 함께).
