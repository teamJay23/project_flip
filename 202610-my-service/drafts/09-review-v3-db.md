## 08 세션 DB 계획

### [꼭 고칠 것]

**K-2. 공개 웹 앱 주소로 아무나 쓸 수 있는 위험 — 대책이 한 줄뿐이다 (08 3-4번 마지막 줄)**
- 근거: 08 3-4번 "웹 앱 주소를 아는 누구나 가짜 기록을 보낼 수 있다. MVP에서는 값 검사(정해진 `type`만, 길이 제한)만 하고 받아들인다."
- 웹 앱 주소는 브라우저 코드(`config.js`)에 들어가므로 결국 공개된다(02 2-2번).
- 위험 세 가지:
  1. **가짜·장난 기록:** 누구나 아무 `session_id`로 `events`를 보낼 수 있다. Phase 3 분석(완료율, 라운드 수)이 틀어진다. 지금은 가짜인지 가릴 방법이 없다.
  2. **대량 쓰기:** 반복해서 보내면 다음과 같은 일이 생긴다.
     - 시트 한도(2,000만 셀)를 채운다.
     - Apps Script 하루 한도를 쓴다.
     - `generate` 요청이면 **Gemini 무료 한도까지 다 써서** 실제 사용자에게 "잠시 후 다시 시도해주세요"가 뜬다.
     - `Code.gs`와 합치면(08 3-4번) 저장 요청과 AI 요청이 같은 주소로 들어온다.
  3. **수식 주입:** `setValues`로 쓴 글이 `=`로 시작하면 시트가 계산식으로 실행한다. 사용자 원문, AI가 만든 카드, 공격자가 보낸 `events` 값 모두 해당한다. 예를 들어 `=IMPORTXML("http://…")` 같은 식이 팀원이 시트를 열 때 바깥 주소로 요청을 보낼 수 있다.
- 고치는 방법 (MVP 최소안, 코드 몇 줄 수준):
  - **값 검사를 구체적으로 적는다:**
    - `type`은 화이트리스트(`know`/`dont_know`/`complete`/`restudy`/`new_stack`/`guide_view`)만 받는다.
    - `session_id`는 UUID 모양만 받는다.
    - `card_order`는 1~20, `round`는 1~50 같은 작은 정수만 받는다.
    - 요청 1번에 `events` 최대 줄 수를 정한다(예: 20).
    - 글자 칸은 길이를 제한한다.
  - **수식 막기:** 시트에 쓰는 모든 글 값 앞에 `'`(작은따옴표)를 붙이거나, 탭의 서식을 "일반 텍스트"로 고정한다. 그러면 `=`로 시작해도 글로 저장된다.
  - **간단한 하루 상한:** Apps Script가 하루 쓰기 줄 수 또는 `generate` 호출 수를 세어, 넘으면 거절한다. `PropertiesService`(Apps Script 안의 작은 저장 공간)에 날짜별 숫자를 두면 된다. 02 질문 5와 같은 결정이므로 묶어서 정한다.
  - **한계를 적어 둔다:** 이 방법으로도 "진짜 사용자 기록인지"는 증명할 수 없다. Phase 3 분석 때는 이상한 값(너무 많은 이벤트, 짧은 시간에 몰린 기록)을 걸러 보는 단계를 둔다고 적는다.

**K-3. 기록 쓰기가 실패해도 카드 생성·학습을 막으면 안 된다 — 추천안 C에 이 규칙이 없다 (08 3-3번·6-2번)**
- 근거:
  - 08 3-3번: `stacks`·`cards`는 "카드를 만든 바로 그 실행 안에서" Apps Script가 시트에 쓴다.
  - PRD 기능 7: 실패 문구 3종은 **카드 생성 실패**에 대한 것이다.
  - PRD 6-c: 기다리는 시간은 60초다.
- 문제:
  - 같은 실행 안에서 시트 쓰기가 실패하면, `catch`가 그것을 생성 실패로 바꿀 수 있다. 예: 시트 ID가 잘못됐을 때, `LockService` 대기 시간이 끝났을 때. 그러면 **카드는 잘 만들어졌는데 사용자는 "잠시 후 다시 시도해주세요"를 본다.**
  - 시트 쓰기와 잠금 대기 시간이 60초 예산에 더해진다.
  - 라운드 끝 `events` 전송이 실패하거나 느릴 때, 학습 화면이 멈추거나 오류가 뜨면 안 된다.
- 고치는 방법: 08 3-3번에 규칙 3줄을 더한다.
  1. Apps Script는 **카드 생성 결과를 먼저 정한 뒤**, 시트 쓰기는 별도 `try/catch`로 감싼다. 쓰기가 실패해도 응답은 `ok: true, cards` 그대로 보내고, 실패는 실행 기록에만 남긴다.
  2. `LockService` 대기 시간은 짧게(예: 5초) 두고, 못 잡으면 기록만 건너뛴다.
  3. 브라우저의 `events` 전송은 결과를 기다리지 않는다. 실패해도 화면에 아무것도 띄우지 않는다. 기록은 "있으면 좋은 것"이지 학습 흐름의 일부가 아니다.
- D-2 확인 방법에도 한 줄 더한다: "시트 ID를 일부러 틀리게 해도 카드는 정상으로 보인다."

- PRD v1.5 위반, 범위 밖 기능, 키 노출, 근거 없는 숫자는 새로 생기지 않았다.
  - 새 숫자(5초, 1~50, 20줄, 500자)는 모두 "예" 또는 "만들면서 정함"으로 표시되어 있다.
  - 하루 상한 숫자는 팀 질문으로 남겼다.
