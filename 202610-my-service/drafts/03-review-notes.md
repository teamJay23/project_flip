**02-1. 6-a(다른 앱 갔다 오기)와 60초 시간 제한을 어떻게 만들지 빠져 있다**

  - 02 7번 2-7 "로딩 중 다른 앱 갔다 오기"에 할 일이 시험만 있다.
- 문제:
  - 휴대폰 브라우저는 백그라운드에서 `setTimeout`(정해진 시간 뒤 실행하는 타이머)을 늦추거나 멈춘다.
  - 오래 나가 있으면 진행 중인 요청을 끊기도 한다.

- 고치는 방법 (단순한 것만):
  - 시작 시각을 기록해 둔다(`Date.now()`).
  - 화면에 돌아왔을 때(`visibilitychange` = 화면이 다시 보일 때 오는 신호) 지난 시간을 계산한다. 60초가 지났으면 "서비스 문제"를 띄운다.
  - 결과가 도착하면 바로 화면에 반영한다.
  - 다음 경우를 어떻게 할지 팀 질문으로 적는다: "돌아왔을 때 요청이 끊겨 있으면 어떤 문구를 보일지 (서비스 문제를 추천)".
- 2-7 단계에 위 설계를 적어 둔다.

**02-2. "fetch 자체가 실패 = 인터넷"으로 나누면 서비스 고장도 "인터넷" 문구가 된다**
- 근거:
  - 02 6번 검사 표 2번 "인터넷 끊김 (`navigator.onLine === false` 또는 fetch 자체가 실패)"
  - PRD 기능 7 표: "그 밖에 카드 만들기 자체가 실패함 = 서비스 문제"
  - PRD 기능 7: 원문 탓이 아닌 실패에 엉뚱한 문구가 나오면 사용자가 헷갈린다는 이유
- 문제: fetch는 인터넷이 멀쩡해도 실패할 수 있다. 예를 들면:
  - 웹 앱 주소가 틀렸을 때
  - Apps Script 배포 권한이 잘못됐을 때
  - 브라우저가 다른 주소로의 요청을 막았을 때(CORS)
- Apps Script가 처리 중에 멈추면 JSON 대신 HTML 오류 페이지가 와서 `res.json()`이 실패한다. 이것도 "인터넷"으로 분류될 수 있다.
- 기존 `sheet-test.html`의 `fetchJson()`(144~156줄)은 모든 실패를 `null` 하나로 돌려준다. 그래서 그대로 가져다 쓰면 실패 종류를 아예 나눌 수 없다.
- 고치는 방법:
  1. **보내기 전에** `navigator.onLine === false`인지 본다. 꺼져 있으면 "인터넷" 문구를 보이고 보내지 않는다. 지금 표의 1번(60초)과 2번(인터넷)의 순서가 반대다.
  2. 보낸 뒤 fetch가 실패했을 때, `navigator.onLine`이 여전히 true이면 "서비스 문제"로 본다.
  3. JSON 읽기 실패도 "서비스 문제"로 본다.
  4. 시간 초과(abort = 요청 중단)도 "서비스 문제"로 본다. 이 경우는 다른 실패와 구분해서 기록한다.
  5. `fetchJson()`은 재사용하지 않거나, 실패 종류를 돌려주게 바꾼다고 계획에 적는다.

**02-3. Apps Script에서 "키 오류 / 사용량 초과"를 어떻게 알아낼지 빠져 있다 → 7-d를 확인할 수 없다**
- 근거:
  - PRD 7-d "API 키를 일부러 틀리게 바꾸고 … 개발자 기록에 키 오류가 남는다"
  - 02 5번 표 `reason: "KEY"`, `"QUOTA"`
- 문제: Apps Script에서 외부 주소를 부를 때 쓰는 `UrlFetchApp.fetch`는 기본 설정에서 상대가 오류 응답(4xx·5xx)을 주면 바로 예외를 던진다. 그러면 모든 실패가 `catch` 하나로 모여 `OTHER`가 된다. KEY와 QUOTA를 나눌 수 없다.
- 고치는 방법: 2-3 단계에 두 가지를 적는다.
  1. `muteHttpExceptions: true` 옵션을 쓴다 (오류 응답도 예외 없이 받아서 직접 보는 설정).
  2. 응답 상태 코드를 `reason`으로 바꾸는 규칙을 정한다. 예: 키 오류 → `KEY`, 429(요청 너무 많음) → `QUOTA`.
- Gemini가 키 오류에 정확히 어떤 상태 코드를 주는지는 2-3에서 키를 일부러 틀리게 넣어 **직접 확인한 뒤 적는다.** 추측으로 적지 않는다.

**02-10. 무료 등급은 "팀 테스트용"으로만 써야 한다. 실제 사용자 원문을 보내면 약관과 부딪힌다**
